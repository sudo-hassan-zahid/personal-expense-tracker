# Bugs And Optimization Audit

This audit is based on a repo pass of the current Next.js, Supabase, and dashboard code. Severity is about user impact, not implementation difficulty.

## Critical Bugs

| Severity | Area                         | Issue                                                                                                                                                                                                                                                           | Evidence                                                                         | Suggested fix                                                                                                                                                      |
| -------- | ---------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| P0       | Edit transaction type switch | Switching an income to expense, or expense to income, deletes the original record first and then inserts the new one. If the insert fails because of validation, duplicate detection, storage, or network trouble, the original is already soft-deleted.        | `components/EditTransactionModal.tsx`, `actions/expense.ts`, `actions/income.ts` | Create the replacement first, then soft-delete the original only after success. Return and handle errors instead of always closing the modal.                      |
| P0       | Edit transaction type switch | When switching type, the form field names do not match the new action in all cases. Example: changing income to expense renders `name="category"` only after state changes, but existing default value can be empty, making accidental validation failure easy. | `components/EditTransactionModal.tsx`                                            | Add explicit migration logic that builds a clean `FormData` payload for the target type and preserves the previous category/source when possible.                  |
| P0       | Bulk update                  | Bulk category/source update lets users apply any selected category name to both expenses and incomes. Mixed selections can put an income source into expense category, or an expense category into income source.                                               | `components/TransactionList.tsx`, `actions/expense.ts`, `actions/income.ts`      | Split bulk category/source controls by selected type, or disable category bulk update when both types are selected. Validate category/source type on the server.   |
| P0       | Import                       | CSV import loops through rows and calls `addIncome`/`addExpense` one at a time. Partial imports are reported as success, skipped rows are not explained, and duplicate detection can silently reduce the imported count.                                        | `actions/import.ts`                                                              | Add a preview/validation pass, show row errors, and return imported/skipped/failed counts. Consider batched inserts after validation.                              |
| P0       | Cache isolation              | `getDashboardData` uses `"use cache"` with broad cache tags and accepts cookies/userId. If cache keying is wrong or unstable, user-specific data caching can become risky.                                                                                      | `lib/dashboard-data.ts`, `app/dashboard/page.tsx`                                | Verify Next cache behavior for user-specific cached functions. Prefer per-user cache keys only, or remove cache from authenticated user data until confirmed safe. |

## High Priority Bugs

| Severity | Area                 | Issue                                                                                                                                                                                                      | Evidence                                                           | Suggested fix                                                                                                            |
| -------- | -------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------ |
| P1       | Dashboard totals     | Dashboard totals use the currently loaded filtered transactions, while budget progress uses `initialExpenses` only. This can make totals, chart, and budgets disagree depending on selected period/search. | `components/DashboardContent.tsx`, `components/BudgetProgress.tsx` | Decide whether budget progress follows dashboard filters or always current month, then label and query it consistently.  |
| P1       | Planning dates       | Planning and budgets use `new Date()` server time, while dashboard filters use PKT helpers. Month boundaries can differ by deployment timezone.                                                            | `actions/planning.ts`, `lib/dashboard-filters.ts`                  | Use one date utility/timezone policy for all month calculations.                                                         |
| P1       | Recurring posting    | Posting due recurring items inserts transactions and then advances schedules. If schedule updates fail after inserts succeed, duplicate posting can happen later.                                          | `actions/planning.ts`                                              | Use a database transaction/RPC for insert-and-advance, or mark processed IDs before insertion.                           |
| P1       | Category links       | Transactions store category/source as text. Renames attempt to propagate text changes, but failures are not checked.                                                                                       | `actions/category.ts`                                              | Check propagation errors and consider storing `category_id` long-term while keeping display text denormalized if needed. |
| P1       | Deleted categories   | Category delete checks all linked transactions, including soft-deleted ones. Users may be blocked by old deleted records.                                                                                  | `actions/category.ts`                                              | Filter linked checks with `.is("deleted_at", null)` for expenses/incomes.                                                |
| P1       | Attachment lifecycle | Deleting an expense soft-deletes the row but leaves the attachment file in storage. Editing does not replace/remove attachments.                                                                           | `actions/expense.ts`, `app/dashboard/attachments/route.ts`         | Add remove/replace attachment actions and decide whether permanent cleanup runs during account-data deletion.            |

## Optimization Points

| Priority | Area             | Observation                                                                                                                                                                     | Recommendation                                                                                                               |
| -------- | ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| P0       | Pagination       | Data loading fetches all matching expenses and incomes, then client-side pagination slices the merged list. Large accounts will slow down.                                      | Add server-side pagination for the combined transaction feed, or fetch limited windows from both tables and merge carefully. |
| P0       | Search           | Search runs both in Supabase for dashboard filters and again in `useTransactions` for the loaded list. Users may see confusing differences between URL search and table search. | Use one search model per view. If URL search is primary, hydrate the client field from it.                                   |
| P1       | CSV import       | Row-by-row server actions create many auth/client calls and revalidations.                                                                                                      | Validate all rows once, then batch insert expenses and incomes separately. Revalidate once.                                  |
| P1       | Revalidation     | Many actions revalidate broad tags like transactions/categories/profile.                                                                                                        | Use narrower tags such as `transactions-${user.id}` and `categories-${user.id}`.                                             |
| P1       | Chart            | Chart builds every day in selected range. Very large ranges create large arrays and slow Recharts rendering.                                                                    | Aggregate by day for short ranges, by week/month for long ranges.                                                            |
| P1       | Client bundle    | Dashboard imports several heavy interactive components on the main client surface.                                                                                              | Keep charts dynamic and consider moving rarely used forms like split expense/import into lazy panels.                        |
| P2       | Database indexes | Existing indexes cover common date/deleted filters, but search and category/source filters can still be expensive.                                                              | Add targeted indexes after measuring common queries, especially `(user_id, category, date)` and `(user_id, source, date)`.   |

## Reliability And UX Cleanup

- Do not close edit modals until the server action result is successful.
- Show imported row counts in the toast, not just "Import completed."
- Disable bulk apply when no bulk field is selected.
- Reset selected transactions after filters hide selected rows, or show "selected outside current view."
- Add clear empty states for new accounts with direct "add first expense" and "add first income" actions.
- Use one term consistently: category for expenses, source for income.
- Replace "Financial Performance Analytics" with simpler dashboard language such as "Monthly Overview" or "Cash Flow."

## Supabase And Security Notes

- RLS is enabled for core tables and storage policies correctly scope attachment paths by user folder.
- The `handle_new_user` trigger is `security definer` in `public`. Supabase commonly uses this pattern, but keep function privileges tight and avoid using user-editable metadata for authorization.
- Storage upload accepts any `File` passed by the form. Add file size and MIME type checks before upload.
- Account data deletion deletes database rows but does not visibly delete storage objects. Add attachment cleanup or document the limitation.

## Testing Gaps To Close First

- Unit tests for `validateTransactionInput`, `parseDashboardFilters`, and CSV parsing.
- Integration tests for add/edit/delete income and expense actions.
- Regression test for type switching failure behavior.
- Import tests covering invalid rows, duplicates, quoted commas, and partial failures.
- RLS smoke test or Supabase local test for user isolation on all user-owned tables.
